# 2，cli的书写规范
    1. main 返回 int（退出码），不直接 exit —— 测试能直接调用 main(...) 拿返回值，不用起子进程
    2. 退出码协议：0=成功 / 1=业务失败 / 2=用法错误（UNIX 惯例，CI/调度系统都认）
    3. 错误走 stderr，正常输出走 stdout —— 脚本和 CI 才能分别捕获
    4. 业务逻辑和 CLI 外壳分离 —— 业务放 run()，可单独测试、可被其他入口复用

 二、为什么这么写，而不是在模块顶部写一行全局 parser = argparse.ArgumentParser(...)

  1. 纯函数，只做一件事。它不读 sys.argv、不碰全局状态、不打印任何东西，只负责"把解析器造好"。真正读命令行是 main() 里
     parse_args(argv) 干的（core/cli.py:88）——构建（build）、解析（parse）、执行（act）三个环节分开，这就是文件
     docstring 里说的 argparse 三件套。
  2. 可测试。函数边界清晰，测试里可以传假参数：build_parser().parse_args(["--table", "x", "--data",
     "y"])，不用真的启动命令行子进程。如果 parser 是模块级全局变量，测试之间还会互相污染状态（argparse
     解析时会在对象上累积内部状态）。
  3. 每次调用都是全新实例。main() 每次运行都拿到一个干净的 parser，不会有"上一次解析残留"的问题。
  4. -> argparse.ArgumentParser 类型注解在告诉你：这个函数产出什么，别人拿到返回值能干什么。

  顺带澄清一个容易混的点：core/cli.py:13-14 导入的 run_checks 和 load_rules 不在 build_parser() 里面用——它们是 main()
  在解析完参数后调用业务逻辑用的（core/cli.py:90,105）。build_parser() 只依赖标准库和自己文件里的 DEFAULT_CONFIG。

  四、它在哪里被使用

  全项目只有一处调用（core/cli.py:88）：

  args = build_parser().parse_args(argv)

  注意这是链式调用：build_parser() 返回 parser 对象，紧接着在返回值上调用 .parse_args(argv)，一步完成"造解析器 +
  解析参数"。argv 平时为 None（argparse 自己去读真实命令行），测试时可以传入模拟参数列表。

  最后，这么写还有个实际收益：required=True、--help 说明、拼错参数名的提示，都由 argparse 白送——build_parser()
  只是在声明"这个命令长什么样"，声明的过程就是帮 dqm 把 CLI 的"规格"写下来。
