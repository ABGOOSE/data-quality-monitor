# 2，为什么要这么做（每个决定背后的理由）
    - 为什么要实现表级规则：rules.yaml 里声明了 row_count 却没人执行——配置和代码脱节，
      这正是契约测试要防的事，说明光有配置机制不够，调度代码必须真去执行它
    - 为什么未知规则名要报错而不是跳过：监控工具最危险的失败方式不是报错，
      是"安静地没干活"——你以为在查，其实没查，数据质量问题悄悄漏掉。宁可崩溃也不假装通过
    - 为什么要两张分派表：列级函数收 Series、表级函数收 DataFrame，签名不同，
      分开登记，run_checks 才知道该传什么
    - 为什么 min 改成 min_rows：参数键名必须和函数签名对齐，契约测试才守得住——
      原则是"规则文件跟着代码走，不是代码迁就规则文件"
    - 为什么结果统一补 column 键：列级放列名、表级放 None，
      输出报告时只用一套代码，不用为表级规则另写分支
    - 为什么 CLI 用 argparse 而不是手写 if：缺参、拼错参数名、--help 全是白送的
    - 为什么要退出码协议：0=全过、1=有失败、2=用法错误——CI 和将来的 Airflow
      不看你打印了什么，只看退出码
    - 为什么要 pip install -e：开发期改代码立刻生效，不用每次重装
    - 为什么 CI 里要加 CLI 冒烟测试：单测保证函数逻辑对，
      但"读配置→读数据→跑检查→退出码"整条链路通不通，只有真跑一次才知道
    - 为什么坏数据那条冒烟测试要用 ! 反转：把"必须失败"的行为也验证掉，
      防止哪天 CLI 坏到连违规数据都退出码 0 也没人发现

# 3，新知识速查：用途和用法（今天最值钱的资产）

## 3.1 语法类

### 字典分派表（dispatch table）
用途：把配置里的字符串翻译成可以调用的函数——规则引擎的核心机制。
用法：
```python
RULE_FUNCTIONS = {"not_null": check_not_null, "unique": check_unique}
func = RULE_FUNCTIONS[rule_name]   # 字符串 -> 函数
result = func(series, **params)
```
以后加规则 = 写函数 + 登记一行，调度代码不用改。

### dict.get(key, 默认值)
用途：读配置时容忍"这个段没写"，返回默认值而不是 KeyError。
用法：
```python
table_rules.get("columns", {})   # 没写 columns 段 -> 空字典，循环自然跳过
table_rules.get("checks", [])    # 没写 checks 段 -> 空列表
```

### 字典推导式
用途：从一个字典里剔除某些键，得到"纯参数"字典。
用法：
```python
params = {k: v for k, v in rule_config.items() if k != "rule"}
# {"rule": "range", "min_value": 0} -> {"min_value": 0}
```

### **params 字典解包
用途：把字典展开成关键字参数传给函数。这就是"YAML 键名必须对齐函数签名"的原因——
键名错了，函数会直接报"unexpected keyword argument"。
用法：
```python
func(series, **{"min_value": 0, "max_value": 1000000})
# 完全等价于 func(series, min_value=0, max_value=1000000)
```

### 函数默认参数
用途：参数可省略，调用方不传就用默认值；配置里不写这个键也不会报错。
用法：
```python
def check_row_count(df, min_rows: int = 1):  # 不传 min_rows 就用 1
```

### inspect.signature（反射）
用途：运行时把函数签名读出来当数据用。契约测试靠它把 YAML 键名和参数名做差集比较。
用法：
```python
import inspect
sig = inspect.signature(func)
param_names = set(sig.parameters)   # 例如 {"df", "min_rows"}
```

### if __name__ == "__main__"
用途：一个文件既能被 import 当模块用，又能直接运行。
import 时只拿函数不执行；python -m core.cli 时才执行 main。
用法：
```python
if __name__ == "__main__":
    sys.exit(main())
```

### sys.exit 与退出码
用途：把 main 的返回值变成进程退出码。退出码是 CLI 和 CI/调度系统之间的"协议"，
它们不读你打印的文本，只看这个数字。约定：0=成功，非 0=失败。
用法：
```python
return 0 if all(r["passed"] for r in results) else 1
sys.exit(main())
# 终端验证：跑完命令后 echo $? 看退出码
```

### Path(__file__).resolve().parents[1]
用途：用文件自身位置动态定位项目根，无论从哪个目录运行都找得到配置文件。
用法：
```python
Path(__file__).resolve().parents[1] / "config" / "rules.yaml"
# parents[0] = core/，parents[1] = 项目根
```

### stdout 和 stderr 分开
用途：正常报告走 stdout，错误信息走 stderr。两个通道分开，
脚本和 CI 才能把"正常输出"和"报错"分别捕获。
用法：
```python
print("检查报告")                      # 默认 stdout
print("Error: 表不存在", file=sys.stderr)   # 错误通道
```

### 三元表达式
用途：一行版的 if-else，适合给变量按条件取值。
用法：
```python
status = "PASS" if result["passed"] else "FAIL"
```

### YAML 语法速记（早上补课）
用途：项目配置格式，声明规则不写代码。
用法要点：缩进=层级；冒号后必须有空格；禁 Tab；键重复会被静默覆盖（写错键名不报错，要小心）。

### pyyaml 的 safe_load
用途：把 YAML 文件翻译成 Python 字典。
用法：必须用 yaml.safe_load（防任意代码执行），不要用 yaml.load。
```python
with open("rules.yaml", encoding="utf-8") as f:
    rules = yaml.safe_load(f)
```

## 3.2 测试类

### pytest.raises
用途：断言某段代码必须抛出指定异常。match 参数用正则匹配报错信息，
防止"抛了 ValueError 但原因完全不对"的假通过。
用法：
```python
with pytest.raises(ValueError, match="no_such_rule"):
    run_checks(df, table_rules)
```

### 契约测试
用途：守住"配置和代码的一致性"——YAML 声明的每条规则必须有同名实现、
每个参数必须能被函数签名接收。
和单测的区别：单测查"函数行为对不对"，契约查"配置和代码有没有脱节"。
用法：见 tests/test_config_loader.py，写进 CI 每次自动跑。

### 边界值测试
用途：专门抓 >= 误写成 > 这类"差一点"的 bug。
用法：min_rows=2 时，恰好 2 行的表必须 PASS（tests/test_checker.py 里有）。

## 3.3 打包与安装类

### pip install -e .（editable 可编辑安装）
用途：开发期安装，只登记一个指针指向项目目录，改代码立刻生效，不用重装。
用法：
```bash
pip install -e ".[dev]"   # .[dev] = 本项目 + dev 可选依赖组（pytest、ruff）
```

### [project.scripts] 命令入口
用途：安装后自动生成命令行工具，终端直接敲命令名。
用法（pyproject.toml）：
```toml
[project.scripts]
dqm = "core.cli:main"   # 命令名 = "模块路径:函数名"
```

### [build-system] + packages.find
用途：告诉 pip 用什么工具构建、哪些目录是代码包。
flat-layout（没有 src/ 目录）下必须显式声明，否则 setuptools 报
"Multiple top-level packages" 拒绝猜测。
用法（pyproject.toml）：
```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[tool.setuptools.packages.find]
include = ["core*", "config*"]
```

## 3.4 CI 类（.github/workflows/ci.yml）

### workflow 四要素
- on：什么时候跑（push 到 main、任何 PR）
- jobs：跑什么任务
- matrix：同一份 steps 在多个 Python 版本各跑一遍，防用了新版本才有的语法
- steps：按顺序执行的步骤（装依赖 -> lint -> 测试 -> 冒烟）
- cache: pip：缓存依赖包，第二次跑不用重新下载

### bash 的 ! 取反
用途：把"命令失败"变成"这一步成功"——用来验证"这条命令必须失败"。
用法：
```yaml
run: |
  ! dqm --table sample_orders --data data/sample_orders_bad.csv
# 坏数据必须退出码 1；如果 CLI 坏了返回 0，! 会让这一步变红
```

## 3.5 CLI 类

### argparse 三件套
用途：命令行参数解析，--help、缺参报错、拼错提示全是白送的。
用法：
```python
parser = argparse.ArgumentParser(prog="dqm")          # 1. 创建解析器
parser.add_argument("--table", required=True)          # 2. 声明参数
parser.add_argument("--config", type=Path, default=x)  # type 自动转换，default 可省略
args = parser.parse_args()                             # 3. 解析
print(args.table)   # 参数值都在 args 对象上
```
